# 0021 Generated test media corpus

- Status: Proposed
- Date: 2026-10-29
- Refines: "Verifikation" in `docs/plan.md`

## Context

Playback correctness depends on a broad matrix of containers and codecs. Committing media
files would bloat the repository and raise licensing questions. The dev machine is Windows,
while CI and Docker run Linux.

## Decision

- The corpus is generated by a **Go program** at `scripts/gen-testmedia` (`go run
  ./scripts/gen-testmedia`). It works the same on Windows and Linux without shell scripts.
- Inputs are only FFmpeg `lavfi` sources (`testsrc2`, `sine`, `color`, …) and text the
  program writes itself, so every file is free of third-party rights.
- Cases are declared as data (name, output file, FFmpeg args, required encoders and muxers,
  expected container and codecs). Before running, the program reads `ffmpeg -encoders` and
  `ffmpeg -muxers` and **skips** cases it cannot build, with a reason.
- Output goes to `testdata/media/` (git-ignored) plus `manifest.json`, which lists every case
  as generated or skipped with expected properties. Integration tests read the manifest and
  skip cleanly when the corpus or FFmpeg is missing.
- Known gaps (no FFmpeg encoder or text→bitmap path): PGS and VobSub/DVB subtitles, APE, DSD
  (DSF/DFF), HEIC, RealVideo 4, EXIF in photos. The manifest marks them as gaps. They are
  covered later by small, freely licensed sample files or other tools (for example exiftool),
  each through its own task.

## Consequences

- The corpus is reproducible on every machine. Its contents depend on the local FFmpeg build;
  the manifest makes that visible.
- Generation takes time, so it is idempotent: existing files are kept unless `-force` is
  given.
